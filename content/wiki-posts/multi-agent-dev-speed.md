멀티 에이전트 개발(Multi-Agent Development)의 속도는 코드보다 먼저 정하는 API 스펙에서 갈립니다. 서버와 앱이 주고받을 엔드포인트(Endpoint) 목록을 먼저 확정하면 서버 에이전트와 앱 에이전트가 기다리지 않고 동시에 구현합니다. 사람은 이 목록만 읽어도 빠진 기능을 구현 전에 찾아냅니다.

순서는 세 단계입니다. 스펙을 확정하고, 사람이 검토하고, 두 에이전트가 병렬로 구현합니다.

## 멀티 에이전트 개발에서 왜 API 스펙부터 정하나요?

엔드포인트 목록이 서버와 앱의 통신 방식을 정하는 공통 사항이기 때문입니다. RESTful 엔드포인트 목록을 먼저 정해 두어야 서버와 앱을 병렬로 개발할 수 있습니다.

앱 개발은 크게 백엔드 서버와 클라이언트 앱으로 나뉩니다. 두 영역을 따로 개발하려면 경계에서 주고받을 규약을 먼저 고정해야 합니다. 규약 없이 동시에 돌리면 두 에이전트가 서로 다른 경로와 데이터 구조를 가정합니다. 그러면 통합 단계에서 맞지 않는 부분을 다시 짜야 합니다.

반대로 서버가 끝날 때까지 앱 에이전트를 세워 두면 에이전트를 여럿 쓰는 이점이 사라집니다. 스펙을 먼저 확정하는 방식은 이 두 문제를 함께 피합니다.

## 순차 개발과 스펙 선행 병렬 개발 비교

스펙을 먼저 확정하면 전체 시간을 줄일 수 있습니다. 순차 개발은 서버 시간과 앱 시간을 더한 만큼 걸립니다. 스펙 선행 방식은 스펙 작성 시간에 둘 중 긴 쪽만 더하면 됩니다.

에이전트 하나가 서버와 앱을 차례로 만드는 방식은 순차 개발과 다르지 않습니다. 스펙이 고정되면 일을 나눌 수 있습니다. 서버 에이전트는 스펙을 충족하는 컨트롤러와 비즈니스 로직을 구현합니다. 앱 에이전트는 같은 스펙을 보며 화면과 네트워크 호출 계층을 구현합니다.

순차 개발, 규약 없는 병렬 개발, 스펙 선행 병렬 개발을 나란히 놓으면 차이가 드러납니다.

| 항목 | 순차 개발 | 규약 없는 병렬 | 스펙 선행 병렬 |
| --- | --- | --- | --- |
| 먼저 만드는 것 | 서버 구현 코드 전체 | 없음, 에이전트가 각자 가정 | 엔드포인트 목록과 API 스펙 |
| 서버·앱 진행 | 서버가 끝난 뒤 앱 착수 | 동시에 하지만 규약이 어긋남 | 같은 스펙을 보고 동시에 구현 |
| 걸리는 시간 | 서버 시간 + 앱 시간 | 처음엔 빠르나 통합 재작업 증가 | 스펙 시간 + 둘 중 긴 쪽 |
| 누락 발견 시점 | 앱 화면 연동 단계 | 통합 테스트 실패 시점 | 엔드포인트 목록 검토 단계 |

## 엔드포인트 목록을 검토하면 무엇이 보이나요?

빠진 기능과 빠진 데이터 모델이 코드를 쓰기 전에 보입니다. 그래서 에이전트가 제안한 엔드포인트 목록은 그대로 넘기지 않고 사람이 직접 검토합니다.

발견은 꼬리를 물고 이어집니다. 인증 엔드포인트를 예로 들어 봅니다. 초안에 로그인(Sign-in)과 로그아웃(Sign-out)만 있고 회원가입(Sign-up)이 없다는 점이 먼저 드러납니다. 회원가입을 넣으려면 약관 동의를 기록해야 하고, 그러려면 약관 관련 데이터 모델이 필요합니다.

| 검토 단계 | 확인한 내용 | 후속 조치 |
| --- | --- | --- |
| 초안 점검 | 에이전트가 낸 엔드포인트 목록 | 구현 전에 사람이 검토 |
| 기능 누락 | 로그인·로그아웃만 있고 회원가입 없음 | 회원가입 엔드포인트 추가 |
| 정책 요건 | 가입할 때 약관 동의 기록 필요 | 가입 요청이나 동의 기록 API에 반영 |
| 데이터 모델 | 약관과 동의 이력을 저장할 모델 없음 | 약관, 약관 동의 이력 모델 추가 |

엔드포인트 목록을 검토하다 보면 이런 빈틈이 눈에 들어옵니다. 구현 코드를 끝까지 읽으며 빠진 요구사항을 찾는 것보다 목록 한 장을 훑는 편이 부담이 적습니다. 스펙 단계에서 고치면 데이터베이스 스키마와 서버·앱 코드를 뒤늦게 고칠 일도 줄어듭니다.

## 내 프로젝트에 적용하는 4단계 체크리스트

구현 에이전트는 스펙을 확정한 뒤에 실행합니다. 아래 순서로 진행합니다.

1. **엔드포인트 목록부터 뽑습니다.** 기능 요구사항에서 경로, HTTP 메서드, 요청·응답 스키마를 먼저 정리합니다. 서버와 앱이 만나는 접점이 모두 들어갔는지 확인합니다.
2. **흐름이 끝까지 이어지는지 봅니다.** 회원가입, 로그인, 로그아웃처럼 짝을 이루는 엔드포인트 중 빠진 것을 찾습니다. 생성·조회·수정·삭제도 같은 방식으로 점검합니다.
3. **규칙과 모델을 거꾸로 추적합니다.** 추가한 엔드포인트에 따라오는 정책 요건을 적습니다. 그 요건을 받치는 데이터 모델이 스키마에 있는지 확인합니다.
4. **확정한 스펙으로 두 에이전트를 동시에 실행합니다.** 서버 에이전트와 앱 에이전트가 같은 스펙 문서를 참조하는지 확인합니다.

스펙 검토가 설계의 빈틈을 막는다면, 구현 뒤의 품질은 검증 장치가 맡습니다. 에이전트가 쓴 코드의 품질을 지키는 방법은 [AI 코드 슬롭을 막는 코드베이스 장치](/posts/ai-code-slop-prevention)에서 이어집니다. 에이전트 관련 용어가 낯설다면 [AI 엔지니어링 용어 23개](/posts/ai-engineering-terms-23)부터 읽으면 됩니다.

## 자주 묻는 질문

### API 스펙은 어떤 형식으로 적어야 하나요?

경로, HTTP 메서드, 요청·응답 스키마가 들어가면 됩니다. OpenAPI 문서나 마크다운 표처럼 두 에이전트가 함께 참조할 문서 하나로 정리합니다. 문서가 하나여야 에이전트가 제각기 짐작으로 채우는 부분이 줄어듭니다.

### 에이전트가 만든 엔드포인트 목록을 그대로 써도 되나요?

그대로 쓰지 않는 편이 안전합니다. 에이전트 초안에는 회원가입처럼 당연해 보이는 기능이 빠질 수 있습니다. 구현을 시작하기 전에 목록을 한 번 검토하고, 짝을 이루는 흐름에서 빠진 고리가 없는지부터 봅니다.
