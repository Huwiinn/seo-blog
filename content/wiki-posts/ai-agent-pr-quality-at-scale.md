에이전트 PR 품질은 지시문을 늘리는 대신 제약을 검사로 옮겨서 지킵니다. 코딩 에이전트를 쓰면 풀 리퀘스트(PR)의 양은 누구나 늘릴 수 있습니다. 어려운 일은 양이 늘어도 품질이 떨어지지 않는 체계를 만드는 것입니다.

이 글은 그 체계를 운영하는 관점에서 세 가지를 다룹니다. 왜 지시문 대신 코드로 막는지, 코드베이스가 왜 에이전트의 기억인지, 사람은 무엇을 리뷰하는지입니다. 저장소에 넣을 장치의 종류와 적용 순서는 [AI 코드 슬롭을 막는 코드베이스 장치](/posts/ai-code-slop-prevention)에 정리했습니다.

## 에이전트 PR 품질은 왜 지시문 대신 코드로 지키나요?

지시문은 에이전트가 읽고도 어길 수 있지만, 검사는 통과하지 못하면 작업이 거기서 멈추기 때문입니다. 린트(lint) 규칙, 타입, 컴파일러, 테스트는 결정론적입니다. 몇 번을 실행해도 같은 답이 나옵니다.

엔지니어가 시간을 쓸 곳에는 순서가 있습니다. 먼저 투자할 곳부터 적으면 다음과 같습니다.

1. 코드베이스: API 설계, 아키텍처, 리팩토링
2. 정적 분석(static analysis): 린트 규칙, 타입, 컴파일러, 테스트
3. 검증(verification)
4. 글로 쓴 지시: 규칙 파일, 스킬, `AGENTS.md`
5. 사람의 리뷰

흔한 운영은 이 순서를 거꾸로 씁니다. 에이전트가 틀리면 리뷰에서 지적하거나 `AGENTS.md`에 금지 문장을 한 줄 더 적습니다. 순서를 뒤집어 앞의 두 단계에 시간을 먼저 씁니다.

슬롭(slop)은 에이전트가 대충 만들어 낸 저품질 코드입니다. 슬롭을 보는 눈에는 이중 잣대가 끼기 쉽습니다. 내가 에이전트로 만든 큰 PR은 성과로 보이고, 동료가 만든 같은 PR은 슬롭으로 보이기 쉽습니다. 검사는 누가 만든 PR이든 같은 기준으로 봅니다.

## 코드베이스는 왜 에이전트의 기억일까요?

에이전트에게 들어가는 가장 큰 입력 가운데 하나가 기존 코드베이스이기 때문입니다. 코드에 임시방편이 하나 남으면 다음 에이전트는 이를 저장소의 관례로 받아들여 그대로 베낍니다.

임시방편은 이런 경로로 퍼질 수 있습니다. 에이전트가 화면 깜빡임을 고치면서 `setTimeout` 한 줄과 주석을 남깁니다. 그 코드가 공용 모듈로 복사됩니다. 얼마 뒤에는 같은 패턴의 타이머가 저장소 곳곳에 퍼집니다.

이때 근본 원인은 따로 있습니다. 명령형 구조와 선언형 렌더링이 부딪히는 지점을 타이머로 덮은 것입니다. 타이머가 많이 생기고 사라지면 가비지 컬렉션(garbage collection)이 잦아져 앱이 버벅거릴 수 있습니다.

타이머 못지않게 주석도 문제를 키웁니다. 주석에는 제대로 고치려면 손댈 범위가 너무 넓다는 사정이 적힙니다. 다음 에이전트는 그 설명을 근거로 같은 패턴을 따라 하기 쉽습니다.

그래서 엔지니어의 일은 정원 가꾸기에 가까워집니다. 잡초는 코드에 남은 임시방편과 낡은 패턴입니다. 리뷰할 PR이 사람이 다 읽을 수 없을 만큼 늘어나면, 잡초를 하나씩 뽑는 방식으로는 감당하기 어렵습니다.

### 당부는 주석 대신 검사에 남기기

임시방편을 설명하는 주석 대신 린트 규칙을 둡니다. 에이전트가 금지된 패턴을 쓰면 정적 검사가 빌드를 막습니다. 오류 메시지는 증상을 가리지 말고 원인을 고치라고 지시합니다.

### 애매한 기능은 호출부터 막기

잘 쓰려면 섬세한 판단이 필요한 기능일수록 슬롭을 낳기 쉽습니다. 오용하기 쉬운 기능은 일반 제품 코드에서 호출하지 못하게 합니다. 에이전트를 바로잡을 때마다 이런 검사가 하나씩 쌓입니다.

## 사람은 이제 무엇을 리뷰할까요?

코드 대신 검증 결과물을 봅니다. PR이 쏟아진다고 확인을 건너뛰는 것은 아니고, 사람이 보는 대상이 바뀝니다. 리뷰 대상은 에이전트가 남긴 실행 영상, 스크린샷, 아키텍처 다이어그램입니다.

검증의 출발점은 런타임 검증입니다. 에이전트가 앱을 직접 실행하고, 사람이 쓰는 디버깅 도구로 동작을 확인합니다. 여기에 기능 지도(feature map)가 붙습니다. 앱에 어떤 기능이 있고 사용자가 어떤 경로로 그 화면에 닿는지 적어 둔 문서입니다. 이 지도가 있으면 왼쪽 사이드바의 기능이라고만 말해도 에이전트가 찾아가 테스트할 수 있습니다.

형식 검증(formal verification)도 더할 수 있습니다. 상태가 많은 흐름은 TLA+로 모델을 검사하고, 핵심 알고리즘은 Lean으로 증명합니다. 까다로운 버그를 찾는 데 쓸모가 있지만 만능 해법은 아닙니다.

토큰을 쓰는 곳도 바뀝니다. 검증 없이 병합한 PR은 미묘한 버그를 안고 들어올 수 있고, 병합한 뒤에 고치면 시간이 더 듭니다. 그래서 토큰은 코드 생성보다 패치 검증에 더 많이 씁니다.

새 기법이 생긴 것은 아닙니다. 비용이 커서 미뤄 두던 정밀 테스트와 형식 검증을 에이전트에게 맡길 수 있게 된 것입니다.

## 세 가지 운영 원칙과 순서

순서는 기초가 먼저이고 자동화가 나중입니다. 정적 검사와 검증 루프 없이 자동화만 서두르면 슬롭이 더 빨리 쌓이기 쉽습니다. 운영 원칙은 세 가지로 줄일 수 있습니다.

1. 에이전트를 바로잡을 일이 생기면 문장이 아니라 정적 검사로 남깁니다.
2. 제대로 쓰기 어렵거나 애매한 API와 패턴은 아키텍처에서 막습니다.
3. 토큰은 코드 생성보다 확인과 검증에 더 많이 씁니다.

흔한 대응과 나란히 놓으면 생각이 바뀌는 지점이 보입니다.

| 상황 | 흔한 대응 | 검사 중심의 대응 |
| --- | --- | --- |
| 에이전트가 실수함 | `AGENTS.md`에 금지 문장 추가 | 빌드를 멈추는 린트·타입 규칙 추가 |
| 임시방편이 필요함 | 주석으로 사정 설명 | 주석 대신 타입과 검사로 제약 표현 |
| 쓰기 까다로운 API | 리뷰에서 사후 지적 | 제품 코드에서 호출 금지 |
| 사람의 리뷰 | 수천 줄의 변경 내역을 눈으로 읽음 | 영상, 스크린샷, 다이어그램 확인 |

기초가 깔린 뒤에는 릴리스마다 자동 검증 에이전트를 돌릴 수 있습니다. 에이전트 여럿을 동시에 돌리는 방법은 [API 스펙부터 정하는 멀티 에이전트 개발](/posts/multi-agent-dev-speed)에서 다룹니다.

## 자주 묻는 질문

### 주석을 줄이면 왜 품질에 도움이 되나요?

주석을 지우는 것 자체가 이유는 아닙니다. 주석으로 남기던 당부를 빌드를 멈추는 검사로 바꾸기 때문입니다. 주석은 읽고도 무시할 수 있지만 검사는 통과해야 합니다.

### 기여자가 많아져도 품질이 유지되나요?

정적 분석과 자동 검증이 받쳐 주면 유지하기 쉬워집니다. 프로젝트 맥락을 잘 모르는 사람이 PR을 올려도 검사는 같은 기준을 적용합니다. 맥락이 사람의 머릿속이 아니라 검사에 들어 있기 때문입니다.

### 사람 엔지니어의 역할은 사라지나요?

사라지지 않습니다. 엔지니어의 일이 코드를 치는 데서 에이전트가 실수하기 어려운 환경과 규칙, 검증기를 설계하는 쪽으로 옮겨 갑니다.
