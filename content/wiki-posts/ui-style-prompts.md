UI 스타일 이름을 프롬프트에 넣으면 AI가 만드는 화면의 질감과 대비, 배치 방향이 좁혀집니다. 다만 이름은 출발점일 뿐입니다. 누가 쓰는 화면인지, 무엇을 하게 할지, 모바일과 상태 화면은 어떻게 보일지를 함께 적어야 쓸 만한 결과가 나옵니다.

이 글은 글래스모피즘(Glassmorphism)부터 레트로·Y2K까지 10가지 스타일의 생김새와 주의점을 표로 비교합니다. 프롬프트에 넣을 요소와 구현 전 점검 항목도 담았습니다.

## 형용사로 요청하면 왜 비슷한 화면만 나올까요?

AI가 "세련되게 만들어 줘"라는 말을 설계 규칙이 아니라 넓은 분위기 표현으로 받아들이기 때문입니다. 그래서 화면을 여러 장 만들수록 비슷한 카드와 둥근 버튼이 되풀이되기 쉽습니다. 요청할 때 지킬 원칙은 네 가지입니다.

- **스타일 이름만으로는 설계도가 되지 않습니다.** 이름은 질감, 대비, 배치, 장식의 방향을 좁히는 데까지만 씁니다.
- **구조와 행동을 함께 적습니다.** 화면 구조와 행동 유도 버튼(CTA)까지 지정해야 결과를 비교하기 쉽습니다.
- **가독성과 상태를 먼저 요청합니다.** 장식보다 모바일 가독성, 키보드 포커스, 오류·비활성 상태를 앞에 둡니다.
- **콘셉트와 구현을 나눕니다.** AI가 만든 이미지는 방향을 잡는 자료로만 씁니다. 제품 코드는 사람이 디자인 토큰(Design Tokens)을 뽑아 구현하고 테스트합니다.

## UI 스타일 10가지 비교표

UI 스타일은 색상 팔레트가 아니라 설계 규약입니다. 표면의 질감, 요소 사이의 간격, 정보의 시각적 무게를 어떻게 표현할지 정하는 약속이라는 뜻입니다. 같은 대시보드라도 글래스모피즘을 고르면 반투명 패널과 흐림 효과가 중심이 됩니다. 브루탈리즘(Brutalism)을 고르면 굵은 외곽선과 원색 대비 때문에 버튼 모양과 차트에서 강조하는 지점까지 달라집니다.

### 생김새와 어울리는 화면

| 스타일 | 영문 이름 | 눈에 보이는 특징 | 어울리는 화면 |
| --- | --- | --- | --- |
| 글래스모피즘 | Glassmorphism | 반투명 패널, 배경 흐림, 부드러운 경계선 | AI·금융 대시보드, 프리미엄 랜딩 페이지 |
| 브루탈리즘 | Brutalism | 두꺼운 검은 외곽선, 큰 글자, 강한 원색 대비 | 실험적 브랜드 캠페인, 크리에이티브 포트폴리오 |
| 뉴모피즘 | Neumorphism | 배경과 비슷한 표면색, 부드러운 안팎 그림자 | 스마트 기기 제어 앱, 간단한 유틸리티 도구 |
| 벤토 그리드 | Bento Grid | 크기가 다른 모듈형 카드, 명확한 구획 | SaaS 홈 화면, 요약 대시보드 |
| 다크 모드 UI | Dark Mode UI | 어두운 바탕 계층, 제한된 강조색 | 서버 모니터링, 개발자 도구, 오래 보는 화면 |
| 3D·이머시브 | 3D & Immersive | 입체 오브젝트, 재질감, 깊이와 공간감 | 신제품 소개, 브랜드 경험 쇼케이스 |
| 미니멀리즘 | Minimalism | 넓은 여백, 제한된 색상, 중심 행동 하나 | 온보딩, 회원가입, 단일 목적 랜딩 페이지 |
| 그라디언트 메시 | Gradient Mesh | 여러 색이 부드럽게 섞이는 배경 | 크리에이티브 툴, 프로모션 캠페인 |
| 에디토리얼 | Editorial | 잡지형 비대칭 그리드, 강한 헤드라인 | 데이터 스토리텔링, 리포트, 콘텐츠 홈 |
| 레트로·Y2K | Retro / Y2K | 크롬 금속 질감, 픽셀 아이콘, 분홍·보라·청록 색감 | 젊은 고객 대상 캠페인, 엔터테인먼트 |

### 자주 생기는 문제와 프롬프트에 적을 조건

스타일마다 무너지는 지점과 프롬프트에 적을 조건이 다릅니다.

| 스타일 | 자주 생기는 문제 | 프롬프트에 적을 조건 |
| --- | --- | --- |
| 글래스모피즘 | 낮은 대비와 과한 흐림으로 글자가 안 읽힘 | 패널 불투명도, 배경과 글자의 대비, 본문은 불투명 영역에 배치 |
| 브루탈리즘 | 시각적 피로, 작은 화면에서 복잡해짐 | 색상 수 제한, 테두리 굵기 고정, 주요 버튼의 위치와 우선순위 |
| 뉴모피즘 | 버튼의 활성·비활성 상태 구분이 어려움 | 그림자 외에 색상, 라벨, 아이콘으로 상태 구분 |
| 벤토 그리드 | 카드만 늘어 모두 똑같이 중요해 보임 | 핵심 지표 1개, 다음 행동 1개, 참고 정보 3개와 모바일에서 쌓이는 순서 |
| 다크 모드 UI | 회색 본문과 형광 상태색의 대비 부족 | 순수 검정 대신 여러 단계의 어두운 표면, 상태마다 도형과 라벨 병기 |
| 3D·이머시브 | 로딩 비용 증가, 연출이 메시지를 가림 | 3D 오브젝트의 최대 면적, 정적 대체 이미지, 모바일 축소 방식 |
| 미니멀리즘 | 필요한 정보까지 빠져 화면이 비어 보임 | 필수 행동 1개, 필수 설명, 숨길 부가 정보를 구분 |
| 그라디언트 메시 | 배경 채도가 헤드라인과 버튼을 가림 | 본문 카드는 불투명한 흰색 표면, 버튼 주변은 단색 여백 |
| 에디토리얼 | 계층이 많아 읽는 순서가 흔들림 | 결론 문장, 근거 차트, 세부 수치 표, 원자료 링크 순서 |
| 레트로·Y2K | 장식이 많아 버튼과 폼 조작이 어려움 | 프레임과 아이콘만 Y2K로, 본문 서체와 입력 폼은 단순하게 |

## 스타일은 몇 개까지 섞어도 될까요?

주 스타일 1개에 보조 스타일은 1개 정도만 더합니다. 스타일이 여럿 섞이면 AI가 무엇을 먼저 보여 줄지 정하기 어려워지기 때문입니다.

두 스타일은 역할을 나눠 고릅니다. 벤토 그리드로 구조를 잡고 미니멀리즘으로 분위기를 정하는 식입니다. 글래스모피즘, 브루탈리즘, Y2K, 3D를 한 화면에 모두 넣는 경우가 반대 사례입니다. 이렇게 하면 장식만 늘고 화면을 쓰는 목적이 가려집니다.

## AI 프롬프트에는 어떤 요소를 넣어야 할까요?

사용자, 목적, 구조, 행동 순서로 적는 틀을 씁니다. AI가 어떤 분위기로 만들지와 무엇을 구현할지를 함께 이해하게 하기 위해서입니다. 프롬프트에는 네 가지를 담습니다.

1. **사용자**: 누가 어떤 상황에서 쓰는 화면인지 적습니다.
2. **목적과 스타일**: 페이지 종류, 주 스타일과 보조 스타일, 핵심 색상을 정합니다.
3. **구조와 행동**: 첫 화면에서 가장 중요한 행동과 그 전에 보여 줄 정보, 레이아웃을 적습니다.
4. **제약 조건**: 모바일 세로 흐름, 포커스·오류·비활성 상태, 가짜 데이터 금지를 덧붙입니다.

아래는 이 틀에 맞춰 쓴 프롬프트입니다.

```text
러닝 동호회 회원이 쓰는 주간 기록 요약 화면을 만들어 줘.
주 스타일은 벤토 그리드, 보조 스타일은 다크 모드 UI로 하고 강조색은 주황 하나만 써 줘.
가장 큰 카드에는 이번 주 달린 거리를, 그 옆에는 "기록 추가" 버튼을 두고 나머지 카드는 3개만 보여 줘.
모바일에서는 거리 카드, 버튼, 나머지 카드 순서로 쌓고 버튼의 포커스·비활성 상태도 보여 줘.
기록이 없는 칸은 숫자를 지어내지 말고 예시 데이터라고 표시해 줘.
```

첫 두 줄이 사용자와 스타일을 정하고, 다음 두 줄이 구조와 상태 화면을 지정합니다. 마지막 줄은 AI가 숫자를 지어내지 못하게 막습니다. 데이터가 없는 자리는 자리표시자(Placeholder)로 표시하게 합니다.

## 구현 전에 확인할 접근성·성능 체크리스트

AI 시안은 그대로 쓰지 않고 브라우저에서 따로 구현하고 검수합니다. 작업 순서는 일곱 단계입니다.

1. 화면의 목적을 한 문장으로 정합니다.
2. 주 스타일 1개와 보조 스타일 1개를 고릅니다.
3. 제목, 설명, 행동 유도 버튼, 보조 정보의 순서를 먼저 정합니다.
4. 한 번에 한 조건만 바꿔 결과를 비교합니다.
5. 기본, 호버, 포커스, 비활성, 로딩, 오류 상태 화면을 요청합니다.
6. 색상, 간격, 모서리, 그림자, 글자 크기를 디자인 토큰으로 정리합니다.
7. 가짜 데이터를 걷어내고 브라우저에서 반응형과 접근성을 테스트합니다.

점검할 항목은 아래 여섯 가지입니다. 기준은 웹 콘텐츠 접근성 지침(WCAG) 2.2와 Web Vitals입니다.

| 점검 영역 | 확인할 내용 | 관련 기준·기술 |
| --- | --- | --- |
| 명도 대비 | 글자와 배경의 대비 확보, 흐림·그라디언트 위에 긴 문장 금지 | WCAG 2.2 텍스트 대비 4.5:1 이상 권장 |
| 키보드 탐색 | Tab 키만으로 메뉴, 입력 폼, 버튼 이동, 포커스 위치 표시 | `:focus-visible` |
| 색상 비의존 | 상태와 의미를 아이콘, 라벨, 패턴으로 함께 표시 | 색각 다양성 대응 |
| 움직임 제어 | 움직임 감소 설정을 따르고 정적 대체 화면 제공 | `prefers-reduced-motion` |
| 대체 텍스트 | 장식 이미지는 `alt=""`, 정보 이미지는 내용을 서술 | `img` 요소의 `alt` 속성 |
| 미디어 성능 | 차세대 포맷 변환, 해상도 최적화, 지연 로딩 | WebP·AVIF, `loading="lazy"` |

화면의 움직임까지 이름으로 요청하려면 [UI 모션 용어 사전](/posts/ui-motion-dictionary)을 보면 됩니다.

## 자주 묻는 질문

### AI가 만든 UI 이미지를 그대로 서비스에 써도 되나요?

참고용으로는 쓸모가 있지만 그대로 배포하지 않는 편이 안전합니다. 구현 전에 가짜 수치, 로고, 문구, 아이콘을 검토합니다. 동작, 반응형, 접근성, 데이터 정확성은 코드로 구현한 뒤 따로 테스트합니다.

### 생성한 이미지에서 글자가 깨져 나오면 어떻게 하나요?

이미지를 만들 때 글자를 되도록 넣지 않고, 글자 자리를 추상적인 막대나 빈 자리표시자로 요청합니다. 제목과 라벨 같은 실제 글자는 나중에 Figma나 HTML/CSS에서 직접 넣습니다.
