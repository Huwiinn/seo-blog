AI 코드 슬롭은 프롬프트가 아니라 코드베이스에 심은 장치로 막습니다. 슬롭(slop)은 에이전트가 대량으로 만들어 내는 저품질 코드를 말합니다. 글로 쓴 지시는 에이전트가 읽고도 어길 수 있지만, 빌드를 멈추는 검사는 어기면 통과하지 못합니다.

이 글은 그 장치를 다섯 칸으로 나눠 정리하고 내 저장소에 옮기는 순서를 적습니다. 에이전트가 풀 리퀘스트(PR)를 많이 만들 때의 운영 방식은 [에이전트 PR 품질을 지키는 운영 원칙](/posts/ai-agent-pr-quality-at-scale)에서 따로 다룹니다.

## AI 코드 슬롭을 막는 장치는 어디에 둘까요?

지시문이 아니라 코드베이스와 검사 쪽에 둡니다. 글로 쓴 지시는 기계가 강제하지 못하기 때문입니다. 어디에 시간을 쓸지는 다섯 칸짜리 역삼각형인 검증 피라미드로 정리할 수 있습니다.

위 칸일수록 넓고, 시간은 위 칸부터 아래 칸 순서로 씁니다.

| 칸 | 성질 | 둘 수 있는 장치 |
| --- | --- | --- |
| 코드베이스 | 가장 넓음, 결정론적 | 까다로운 API 금지, 폴더 경계, 주석 최소화 |
| 정적 분석(static analysis) | 결정론적 | 수정 지시를 담은 린트(lint) 규칙, 타입 |
| 검증(verification) | 실행 결과로 확인 | 런타임 검증, 형식 검증, 무작위 입력 테스트 |
| 산문(prose) | 좁음, 강제 불가 | 판단이 필요한 내용만 적은 `AGENTS.md` |
| 사람 리뷰(human review) | 가장 좁음 | 코드 대신 실행 영상과 스크린샷 확인 |

규칙 파일과 `AGENTS.md` 같은 산문은 네 번째 칸입니다. 기계 검사로 바꿀 수 없고 판단이 필요한 내용만 조금 적는 자리입니다.

검증 피라미드는 저신뢰 루프(low-trust loop)에서 고신뢰 루프(high-trust loop)로 넘어가는 길입니다. 저신뢰 루프에서는 에이전트가 슬롭을 내고, 사람이 검증하다 뒤늦게 문제를 발견합니다. 고신뢰 루프에서는 에이전트가 좋은 코드를 쓰고 검증까지 맡습니다.

## 코드베이스 칸: 잘못 쓰기 쉬운 것을 구조로 막기

맨 위 칸의 원칙은 사람이 리뷰에서 눈으로 잡던 문제를 구조로 없애는 것입니다. 잘못 쓰기 쉬운 것을 아예 쓸 수 없게 만드는 장치부터 둡니다. 저장소에 남은 패턴은 에이전트가 다음 작업에서 그대로 따라 쓰기 때문입니다.

### 까다로운 API는 제품 코드에서 금지

언제든 쓸 수 있지만 부작용 없이 쓰기는 어려운 API가 있습니다. React의 `useEffect`가 대표적입니다. 에이전트에게 자유롭게 맡기면 무한 렌더링이나 상태 꼬임이 생기기 쉽습니다.

이런 API는 일반 제품 코드에서 호출하지 못하게 막습니다. 프레임워크 계층의 지정된 몇 곳에서만 사용을 허용합니다. 제품 코드는 그 위에 만든 안전한 인터페이스만 씁니다.

### 폴더 이름으로 프로세스 경계 나누기

화면을 그리는 코드와 백그라운드에서 무거운 일을 하는 코드가 섞이면 앱이 버벅거립니다. 두 코드를 최상위 폴더로 나누고, 폴더 사이의 임포트(import)는 린트로 막습니다. 프로세스가 다른 모듈끼리 직접 불러오지 못하게 하는 경계입니다.

### 주석은 거의 쓰지 않기

주석은 예외적인 경우만 남기고 줄이는 편이 좋습니다. 이유는 세 가지입니다.

- 주석은 코드가 바뀌면 금방 낡고, 사람도 잘 읽지 않습니다.
- 에이전트가 근본 해결 대신 임시방편을 택하고 그 이유를 변명하는 도피처가 되기 쉽습니다.
- 다음 에이전트에게 남긴 당부를 기계가 강제하지 못합니다.

지켜야 하는 제약이라면 주석이 아니라 타입이나 검사로 옮깁니다.

## 정적 분석 칸: 교정을 린트 규칙으로 남기기

주석을 줄인 자리는 린트 규칙이 채웁니다. 에이전트를 교정할 때마다 그 내용을 린트 규칙이나 설계로 옮깁니다. 같은 지적을 두 번 하지 않게 만드는 일입니다.

핵심은 오류 메시지입니다. 린트 규칙의 메시지에 임시방편 대신 근본 원인을 고치라는 지시를 구체적으로 담습니다. 빌드가 멈춘 자리에서 에이전트가 바로 읽는 지시문인 셈입니다.

```text
setTimeout으로 실행 시점을 미루지 마세요.
화면이 깜빡이는 원인을 찾아 상태 흐름을 고치세요.
```

교정을 검사로 바꾸는 일을 반복하면 리뷰에서 사람이 지적할 것이 줄어듭니다. 지적할 것이 줄어든 만큼 병합을 에이전트에게 맡기는 범위도 조금씩 넓힐 수 있습니다.

## 검증 칸: 에이전트가 스스로 검증하려면 무엇이 필요할까요?

에이전트가 앱을 직접 실행하고 증거를 남기는 경로가 필요합니다. 병합을 에이전트에게 맡길수록 사람은 코드 대신 영상, 스크린샷, 다이어그램 같은 증거물을 보게 됩니다.

런타임 검증은 터미널 명령 몇 줄이면 됩니다. 실행 중인 앱의 버튼을 누르고, 현재 화면 상태를 확인한 뒤, 결과 화면을 스크린샷 파일로 저장합니다. 그 위에 검증을 여러 겹으로 쌓습니다.

| 검증 기법 | 하는 일 | 어울리는 대상 |
| --- | --- | --- |
| 런타임 검증 | 앱을 직접 조작하고 증거 저장 | 화면 동작 확인과 스크린샷 |
| TLA+ | 가능한 상태를 모두 펼쳐 빠진 예외 탐색 | 여러 기기에 걸친 알림 같은 흐름 |
| Lean | 알고리즘을 수학 증명처럼 확인 | 핵심 알고리즘 |
| 속성 기반 테스트(property-based testing) | 불변 조건에 무작위 입력을 대량 투입 | 손으로 적은 예시 몇 개를 대신함 |
| 퍼징(fuzzing) | 무작위 입력과 조작으로 깨지는 곳 탐색 | 릴리스마다 자동 실행 |

형식 검증은 기존 테스트를 대체하지 않고 검증의 층을 하나 더 쌓습니다. 이런 도구는 쓰고 유지하는 비용이 커서 미뤄 두기 쉬웠습니다. 에이전트에게 맡기면 그 비용이 줄어듭니다.

리뷰를 돕는 장치도 둡니다. 에이전트에게 상태 머신(state machine)을 사용자 관점의 다이어그램으로 그리게 합니다. 실행 영상, 스크린샷과 나란히 놓으면 의도와 동작이 맞는지 확인하기 쉽습니다.

## 내 저장소에 적용하는 순서

안쪽 루프(inner loop)를 먼저 정리하고, 바깥 루프(outer loop) 자동화는 그다음에 올립니다. 코드를 쓰는 안쪽 루프가 슬롭을 내는 상태에서 자동화하면 슬롭이 더 빨리 쌓입니다.

1. `AGENTS.md`에 문장을 보태기 전에, 그 제약을 어기면 빌드가 실패하도록 린트 규칙이나 타입, 테스트로 바꿀 수 있는지 따집니다.
2. 새로 들어오는 코드의 금지 패턴부터 린트로 막습니다. 이미 퍼진 옛 패턴은 그다음에 차례로 치웁니다.
3. 에이전트가 앱을 직접 띄워 조작하고 콘솔 출력이나 스크린샷을 파일로 남기는 명령을 하나 만듭니다. 사람이 코드 대신 증거물을 보게 하는 첫걸음입니다.
4. 안쪽 루프가 깨끗해진 뒤에 바깥 루프 자동화를 연결합니다.

바깥 루프는 외부 신호에서 시작합니다. 사용자 피드백이나 이슈 티켓이 들어오면 에이전트가 수정을 시작합니다. 릴리스 때마다 퍼징을 돌리고 결과를 팀 채팅에 올리는 일도 여기에 속합니다. 이 검증은 새 버그뿐 아니라 코드베이스에 숨어 있던 기존 버그도 찾아낼 수 있습니다.

여러 에이전트를 동시에 돌리는 순서는 [API 스펙부터 정하는 멀티 에이전트 개발](/posts/multi-agent-dev-speed)에서 다룹니다.

## 자주 묻는 질문

### 주석 줄이기와 자동 병합을 바로 따라 해도 될까요?

권하지 않습니다. 검사와 검증이 쌓이기 전에 주석부터 지우고 병합을 맡기면 막아 줄 장치가 없습니다. 반복해서 교정하는 내용을 린트나 테스트로 옮기는 일부터 시작해 AI 코드 슬롭을 줄입니다.

### AGENTS.md 같은 규칙 파일은 쓰지 말아야 하나요?

아닙니다. 기계 검사로 바꿀 수 없고 판단이 필요한 내용만 글로 적으면 됩니다. `CLAUDE.md` 같은 지시 파일에서도 감정적인 강조와 장황한 설명은 걷어내는 편이 좋습니다.

### 장치를 다 갖추면 사람 리뷰는 없어도 되나요?

아닙니다. 사람 리뷰는 검증 피라미드의 마지막 칸으로 남습니다. 다만 보는 대상이 코드에서 실행 영상, 스크린샷, 다이어그램으로 바뀝니다.
