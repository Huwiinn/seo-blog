estudy 실습은 노트를 읽는 데서 끝내지 않고, 핵심 동작을 스스로 예측하고 설명해 보는 복습입니다. 네 가지 랩으로 핵심 동작을 확인하고, 4주 진도표로 백엔드, 인프라, AI 주제를 한 번씩 돕니다.

실습의 재료는 개발자 rlaope가 공개한 학습 사이트 [estudy](https://rlaope.github.io/)입니다. 랩의 조건과 수치는 개인 학습용 로컬 앱의 시뮬레이션에서 가져왔습니다. 이 앱은 사이트의 기능이 아니고 독자가 쓸 수도 없어, 앱 없이 따라 하는 방법으로 정리했습니다. 사이트 전체 구성은 [estudy 지식 베이스 소개 글](/posts/estudy-knowledge-base-overview)에 있습니다.

## estudy 실습은 어떤 순서로 진행하나요?

주제를 찾아 읽고, 랩의 조건에서 결과를 예측하고, 조건을 바꿔 보고, 회상 문제로 점검하는 네 단계입니다.

1. 주제 검색과 노트 정독
2. 랩 표의 조건에서 결과 예측
3. 조건을 바꿔 결과 비교
4. 능동 회상(active recall) 점검과 메모 보관

### 주제를 찾아 읽기

사이트의 지식 그래프 페이지에서 `/` 키를 누르면 검색창으로 들어갑니다. 검색창은 한글 초성 검색을 지원합니다. 주제를 고른 뒤에는 노트를 끝까지 읽습니다.

### 이웃 노트로 범위 넓히기

지식 그래프에서 노드를 선택하고 `e` 키를 누르면 1-hop과 2-hop 이웃만 남습니다. 방금 읽은 노트와 이어진 노트를 여기서 골라 읽습니다. 읽은 뒤에는 자기 말로 학습 메모를 씁니다.

## 아키텍처 랩 4개에서는 무엇을 확인하나요?

랩마다 조건을 읽고 결과를 먼저 예측한 뒤, 아래 표의 확인할 동작과 맞춰 봅니다. 예측이 어긋난 랩은 해당 노트를 다시 읽습니다.

| 랩 | 조건 | 확인할 동작 |
| --- | --- | --- |
| 01 LLM Gateway | Team B의 요청 8건 버스트, 주 경로 장애, Team A의 단건 요청 | Team B가 429 응답으로 막히는 동안 Team A의 토큰 버킷 유지, 장애 시 사내 vLLM으로 우회 |
| 02 PagedAttention & GPU | 독립 요청과 프리픽스 공유 요청 추가, 병렬화 설정 `TP`를 1, 4, 16으로 변경 | 프리픽스 블록 재사용, `TP=1` 적재 실패, `TP=16`에서 36배 대역폭 경고 |
| 03 Dual Cache & PER | 동시 요청 400건, DB 비용 400ms에서 세 전략 비교 | Naive의 DB 쿼리 폭주, Mutex의 락 대기 지연, PER의 P99 방어 |
| 04 ZGC Colored Pointer | Concurrent Relocate 단계에서 객체 필드 읽기 2회 | 1회차는 느린 경로에서 포인터 자가 치유, 2회차부터 빠른 경로 통과 |

### 랩 01과 랩 02: LLM 게이트웨이와 GPU 서빙

랩 01은 한 팀이 요청을 몰아 보내도 대규모 언어 모델(LLM) 게이트웨이가 다른 팀의 토큰 버킷을 지키는 상황입니다. 스스로 답할 질문은 두 가지입니다.

- Team B만 429 응답을 받고 Team A는 영향을 받지 않는 이유는 무엇인가요?
- 주 경로에 장애가 나면 요청은 어디로 가나요?

랩 02는 DeepSeek-V4-Flash(284GB, FP8)를 H200(141GB)에 올리는 계산입니다. `TP` 값을 1, 4, 16으로 바꿔 가며 적재 가능 여부를 따집니다.

- `TP=1`에서 적재가 실패하는 이유는 무엇인가요?
- 프리픽스를 공유하는 요청은 어떤 블록을 다시 쓰나요?
- `TP=16`에서 대역폭 경고가 나오는 이유는 무엇인가요?

두 랩은 [AI 엔지니어링 커리큘럼 글](/posts/estudy-ai-mlops-curriculum)의 LLM 게이트웨이, 서빙 플레이북 부분과 짝을 이룹니다.

### 랩 03과 랩 04: 이중 캐시와 ZGC

랩 03은 Naive Cache-Aside, 분산 Mutex Lock, PER 조기 재계산 세 전략을 같은 조건에서 비교합니다.

- 요청 400건이 한꺼번에 몰릴 때 세 전략의 DB 쿼리 수는 어떻게 달라지나요?
- Mutex는 DB를 지키는 대신 무엇을 내주나요?

랩 04는 ZGC의 포인터 자가 치유 과정을 단계별로 따라갑니다.

- 같은 필드를 처음 읽을 때 느린 경로로 들어가는 이유는 무엇인가요?
- 두 번째 읽기부터 빠른 경로로 통과하는 이유는 무엇인가요?

두 랩은 [백엔드 커리큘럼 글](/posts/estudy-backend-msa-curriculum)의 이중 캐시, JVM 부분과 짝을 이룹니다.

## 조건을 바꿔 보는 과제 4선

확인할 동작을 설명할 수 있으면, 조건을 하나씩 바꿔 결과가 어떻게 달라질지 따져 봅니다.

1. **토큰 리필 속도 변경**: 랩 01에서 토큰 버킷의 리필 속도를 바꾸면 429 응답이 어떻게 달라질지 예측합니다.
2. **DB 비용 변경**: 랩 03에서 DB 비용과 경합 정도를 바꿔 세 전략의 차이를 다시 비교합니다.
3. **유사도 설정값 조정**: 사이트의 지식 그래프는 `related_top_k: 8`, `min_score: 0.04`로 추천 엣지를 만듭니다. 두 값이 달라지면 엣지 밀도가 어떻게 변할지 따져 봅니다.
4. **노트와 연습 문제 추가**: 노트를 1편 읽은 뒤 자기 노트와 연습 문제를 직접 만듭니다.

## 4주 진도표는 어떻게 짜나요?

1~2주차에 백엔드, 3주차에 인프라와 SRE, 4주차에 AI를 배치합니다. 주마다 읽을 범위와 복습 과제를 짝지었습니다.

| 주차 | 읽을 범위 | 복습 과제 |
| --- | --- | --- |
| 1주차 | Server와 MSA | 랩 03 질문에 답하기, 메모 5개 작성 |
| 2주차 | JVM과 DataBase | 랩 04 질문에 답하기, ZGC 자가 치유 정리 |
| 3주차 | 인프라, SRE, 운영체제, 네트워크 | 회상 문제 1회 완주, 오답 재복습 |
| 4주차 | AI, MLOps, 강화학습, 수학 | 랩 01과 랩 02 질문에 답하기, [지식 그래프 UI 분석 글](/posts/estudy-knowledge-graph-ui)과 실제 화면 대조, 메모 백업 |

3주차의 회상 문제로는 과제 4에서 만든 연습 문제를 씁니다. [DevOps·SRE 커리큘럼 글](/posts/estudy-devops-sre-curriculum)의 SRE 50문답을 영역별로 답해 보는 방법도 있습니다.
